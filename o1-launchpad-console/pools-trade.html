What this console actually knows

Reverse-engineered by decoding two real Arc-mainnet transactions (CIRC and ARCO token launches) byte-for-byte — not from a published/verified ABI. Everything below is either confirmed against both transactions, or flagged as unresolved.
Entry point: multicall(bytes[])
Both sample transactions call 0xac9650d8 on the entry contract with an array of exactly 2 inner calls, value = 0.
Call 1: 0xdec14be1 — create token + set metadata
Confirmed top-level fields (both samples): metadata-contract address (0xff99d8f6…bfbf6), string name, string symbol, uint256 decimals (always 18), an address equal to the entry contract itself, then a nested block holding the description/image/website/social strings seen in TokenSocialInfo.md. Not yet confirmed: the exact ABI encoding of that nested 4-string block — standard decoders reject it as currently modeled, so the precise byte layout for the description/website/social fields is not nailed down. Name/symbol/decimals decode cleanly; the rest of the struct does not yet.
Call 2: 0xb6982b48 — launch into the V4 pool
Confirmed fields (both samples): token address, a 32-byte value (see below), the strategy/LP-vault address 0xfe7be4eb…eb056 (constant across both txs — matches POOLS_INSTANT_LAUNCH_STRATEGY_A_ARC), total supply 1e27 (constant), and the connected wallet's own address (verified: equals tx.from in both samples).
Unresolved: the 32-byte value in call 2
CIRC: 0x2a18b644…f211df — ARCO: 0x1bc57832…57efc. Tried keccak256 of the token address alone, of (token, entry), and of (token, name, symbol) — none matched. It is not the V4 poolId either (checked against the real Initialize log). Likely either a CREATE2 salt/commitment or a value that depends on something not visible from these two transactions alone (e.g. an off-chain-signed value, or a value returned by call 1 and threaded into call 2 in a way that can't be reconstructed by only reading calldata). Needs either pools.trade's real frontend network trace or a verified contract ABI to resolve — do not guess this value for a real transaction.
Reference transactions: 0xd4f46f85…4a2a (CIRC) · 0xcdf1c579…f0214 (ARCO).
